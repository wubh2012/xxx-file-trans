NODE-FILE-TRANS · 需求文档

跨网络隔离的单向文件传输系统

在没有网络通道、不允许使用 U 盘等物理介质的两个隔离环境之间，以"屏幕显示 → 摄像头 / 屏幕采集拍摄 → 程序识别还原"为唯一信道，完成文件摆渡。

版本 第三轮修订（协议冻结） 整理日期 2026-09-21 发送端 纯浏览器 Canvas 接收端 Python + OpenCV

一核心问题

内网（发送端）

无法联网，与外网没有任何通信通道；需要把文件送出去。

外网（接收端）

需要拿到内网的文件，但与内网之间无网络、无摆渡介质。

唯一可行的通道是把屏幕本身当作单向光信号发射器：内网屏幕显示黑白方块帧，外网摄像头连续拍摄（或经远程桌面屏幕采集），接收端程序识别并还原文件。

否决的替代方案

方案否决原因
二维码单张容量小、帧率低、容量固定，大文件需成百上千张，不适合连续流式传输
0/1 文字 + OCR误码率高、速度慢；黑白方块直接表示 bit，识别稳定，速度快 5～10 倍

二工作原理

发送端（内网浏览器）文件 → gzip 压缩 → 分片 → 封帧（头部 + CRC32）→ Canvas 渲染黑白方块 → 全屏循环播放
→
单向信道屏幕光信号 / 数字图像采集，摄像头或 mss 抓屏，无任何反向通道
→
接收端（外网 Python）取帧 → 角标定位 → 透视校正 → 采样二值化 → CRC 校验 → 落盘 → 收齐还原 → 通知

协议要点（两端逐 bit 一致）

  • 帧头 208 bit：同步字 0xF0A5、版本、文件 ID、帧号（0xFFFFFF 为元数据帧哨兵）、总帧数、数据长度、分片大小、几何参数（COLS / ROWS / BIT / PAD）、CRC32
  • CRC 冻结为 CRC-32/ISO-HDLC（zlib.crc32 同参），双端自检向量 CRC32(b"123456789") == 0xCBF43926；覆盖头部（除同步字）+ 有效数据字节，补位不计入
  • 元数据帧：携带文件名（UTF-8）、压缩后大小、原始大小、压缩方式——接收端确定落盘文件名与 data.bin 截断长度的唯一来源
  • 取帧源 4 种：camera（锁曝光/对焦/白平衡）、video、images（离线闭环自测主通道）、desktop（mss 抓屏，支持 --region，含变化检测 + 稳定两帧 + 超时强制解码）

三关键约束

全部方案设计都由这三条约束推导而来：

1. 严格单向，无任何反向通道 —— 发送端不知道接收端收到没有。断点续传只能靠"发送端无限循环重播 + 接收端本地持久化去重"。
2. 信道不可靠 —— 摄像头通道有摩尔纹、曝光漂移、帧不同步；desktop 通道有 RDP H.264 压缩伪影、渐进刷新过渡帧。必须靠 CRC32 兜底，坏帧整帧丢弃。
3. 两端参数必须逐 bit 一致 —— COLS / ROWS / BIT / PAD / chunkSize 任何一项错配都会让采样坐标整体偏移、整场解不出。协议把几何参数写进帧头供交叉校验，发送端 UI 回显参数并提供"一键复制接收端命令"。

四功能需求

传输协议

编号需求说明
F1文件分片支持任意文件，gzip 压缩后分片，单文件上限 256 MB
F2帧封装208 bit 帧头 + 数据区，行优先填充、字节内 MSB first，两端写死
F3帧校验CRC-32/ISO-HDLC，错误帧整帧丢弃，不污染文件
F4元数据帧帧号 0xFFFFFF，携带文件名 / plainSize / compressedSize / 压缩方式；每轮首帧 + 每 100 帧插入一次
F5文件 ID 唯一纯内容派生（原始文件字节 CRC32），同文件重开页面 ID 不变，保证续传命中

编号需求说明

F7参数可调BIT / FPS / chunkSize / COLS / ROWS 可配置，按屏自动反推并回显

接收端

编号需求说明
F10四种取帧源camera / video / images / desktop，统一迭代器接口；desktop 含变化检测、稳定两帧、超时强制解码、DPI 感知
F11识别流水线局部自适应阈值 → 角标检测（四条几何一致性约束）→ 透视校正 → 规范画布 Otsu → 5×5 中位数采样

F15进度显示rich 多文件实时进度：帧数 / 百分比 / KB/s / 识别率 / 丢帧；CRC 连续失败告警限流

五非功能需求

编号需求说明
N1容错坏帧丢弃不污染文件；元数据缺失时数据帧照常落盘但不还原
N2持久化meta.json 原子写（tmp + os.replace）；惰性加载未完成任务；还原成功后清理 payload 防磁盘膨胀
N3低依赖发送端纯浏览器单文件、可 file:// 直开、零网络请求；不引入 Electron
N4路径锚定progress/、output/、debug/ 锚定脚本目录，不依赖 cwd；高 DPI 感知
N5性能目标desktop 通道 1 MB 文件 1 分钟内收齐还原；calibrate 识别率 ≥ 99%
N6使用边界跨隔离网络单向摆渡工具，须符合组织安全策略；当前不提供加密与访问控制

六验收标准

  • 离线闭环：发送端导出 PNG + frames.json，接收端 --source images 解码 100% 通过 CRC，逐帧字节一致，gunzip 后 sha256 与原文件一致
  • 桌面通道：本机全屏播放 + --source desktop 整屏捕获，1 MB 文件 1 分钟内收齐还原
  • 校准：calibrate 输出识别率 ≥ 99%，据此确认最终参数
  • 断点续传：中途 Ctrl+C，重启后只补缺失帧并成功还原
  • 续传命中：接收端收一半后重开发送端页面（同一文件），fileId 不变，命中已有进度而非从头开始
  • 参数错配：故意传错 COLS 或 PAD，应全部拒绝并打印期望 / 实际对比，不产生污染文件
  • 误码不污染：抓屏后注入噪点，CRC 拦截全部坏帧，还原文件仍与源一致
  • 元数据缺失保护：屏蔽元数据帧时数据帧照常落盘，收齐后不启动还原
  • 文件名安全：构造 ../../evil.txt、..\..\x、CON，应净化到 output/ 之内
  • 长文件名边界：12 + nameLen 超限的元数据帧应丢弃并告警，不影响数据帧接收
  • 背景干扰：桌面并排打开多个黑色窗口后，角标仍应唯一锁定发送端画面
  • 无摄像头可验证：images + desktop 两条通道覆盖全部功能

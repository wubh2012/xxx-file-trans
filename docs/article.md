# 用屏幕摆渡文件：一个跨隔离网络单向传输系统的原理与实现

> 项目：xxx-file-trans —— 跨隔离网络单向文件摆渡系统
> 事实来源：[需求文档](../需求文档.md) · [协议文档](./protocol.md) · [ADR-0001](./adr/0001-角标编码几何自举.md)

## 一、这个问题为什么存在

设想这样一个场景：一台电脑位于严格隔离的内网里——不能联网，没有共享文件夹，没有 U 盘接口，没有任何网络通道可以把文件送出来。但它的屏幕是亮的。

屏幕是一个天然的**单向光信道**。人可以用手机拍下屏幕上的内容带走，那机器为什么不行？让发送端把文件的每一个字节"画"在屏幕上，接收端用摄像头或抓屏把画面拍下来，再逐像素还原成字节——这就是本项目做的事情，我们称之为"摆渡"。

这个思路并不新鲜，二维码就是它的最著名应用。但二维码解决不了这个问题：

| 方案 | 缺陷 |
|---|---|
| 手工拍照 + OCR | 误码率高，几百 KB 的文件根本不可靠 |
| 二维码轮播 | 单个二维码容量太小（几百字节），大量时间浪费在定位图案和纠错冗余上 |
| 现成条码库 | 面向"一物一码"设计，不适合连续吞吐海量数据 |

摆渡一个几百 KB 到几百 MB 的文件，需要一套**为吞吐量定制**的编码协议、**不依赖人工对齐**的几何识别，以及**严格单向信道下依然可用**的断点续传。这些正是本文要讲的内容。

## 二、系统全貌

整个系统只有两个程序：

```
┌─────────── 内网（隔离侧） ───────────┐          ┌───────── 外网（接收侧） ─────────┐
│                                      │          │                                  │
│  sender.html（浏览器单文件，零依赖）  │          │  python -m receiver（Python CLI） │
│                                      │          │                                  │
│  文件 → gzip 压缩 → 分片 → 封帧      │   光     │  取帧源 ──→ 几何自举 ──→ 采样    │
│  → 黑白方块网格全屏循环播放          │ ══════> │      │                            │
│                                      │  单向    │      └→ CRC 校验 → 位图落盘     │
│  （也可导出 PNG 帧序列做闭环自测）    │  信道    │          → 收齐后 gunzip 还原    │
└──────────────────────────────────────┘          └──────────────────────────────────┘
```

- **发送端**是一个纯浏览器页面（`file://` 直开、零网络请求），内网机器上不需要安装任何软件。选择文件后自动完成压缩、分片、封帧，把每一帧渲染成黑白方块网格全屏循环播放。
- **接收端**是 Python CLI，从四种取帧源拿画面：
  - **camera** —— 摄像头对着屏幕拍（物理隔离最彻底的方式）；
  - **desktop** —— 同机或跨屏时自动优先使用 DXGI（不可用时回退 mss），支持 `--region pick` 冻屏框选任意窗口区域；
  - **video** —— 解析预先录制的屏幕视频，用于离线复盘与批量验证；
  - **images** —— 读 PNG 帧序列，用于端到端自动化测试。

收齐全部数据帧并拿到元数据后，接收端自动 gunzip 还原落盘，最终以 gzip 尾部 CRC + ISIZE 与源文件 sha256 一致，拿到**端到端完整性证明**。

## 三、核心原理：如何把数据变成"类二维码"

### 3.1 一帧画面里装了什么？

先建立直觉：屏幕上那一屏黑白方块，其实是一个"快递包裹"。文件太大装不下一屏，所以拆成成千上万个包裹，屏幕上飞快地一个个展示。打包裹的过程分四步：

```
原始文件 ──① 压缩──▶ 抽真空 ──② 分片──▶ 切成标准箱 ──③ 封帧──▶ 贴面单 ──④ 渲染──▶ 黑白方块
```

**① 压缩（把被子抽真空）。** 文件先做 gzip。文本、表格这类文件往往能压掉一大半，体积小了，传输时间直接减半。这步还有一个免费的额外好处：gzip 数据的末尾自带一份"校验账单"（校验码 + 原始长度），接收端解压成功本身就等于验证了"拿到的文件和原来那个一模一样"——端到端的完整性证明不用额外设计，压缩格式白送的。

**② 分片（切成标准大小的箱子）。** 压缩后的数据被切成等长的小段，一段装一帧。每段装多少不是拍脑袋定的，而是拿屏幕几何算出来的：**整张网格能放多少个方块，减去"快递面单"占掉的位置，剩下的全部装数据**。所以屏幕越大、方块越小，单帧装得就越多——传输参数和屏幕规格是联动设计的。

**③ 封帧（每个箱子贴一张面单）。** 光有数据不行——接收端得知道这是第几个包裹、一共多少个、这箱装了多少。所以每帧开头有一段固定格式的**帧头**，就像快递面单：

| 面单字段 | 通俗含义 |
|---|---|
| 同步字 | "喂，快递来了"——帮接收端对齐从哪个 bit 开始读 |
| 文件 ID | 这个文件的"指纹"（由文件内容算出），重开页面也不变，是断点续传的钥匙 |
| 帧号 / 总帧数 | 第几个包裹 / 一共多少个 |
| 数据长度 / 分片大小 | 这个箱子实际装了多少 / 标准箱多大 |
| 几何参数 | 这张画面上网格的规格（几列几行、方块多大、留白多宽） |
| CRC32 校验码 | 整个箱子（面单 + 货物）的"封条"——途中任何一处被读错，封条就对不上 |

**④ 渲染（把 0 和 1 涂成黑白方块）。** 最后一步简单粗暴：数据本质是一长串 0 和 1，按顺序一格一格填——**黑块代表 1，白块代表 0**。填完加上四角的角标和四周的留白（静默区），就是屏幕上完整的一帧。它看起来确实很像一个巨大的二维码，但没有定位装饰、没有掩码、没有纠错冗余，每一寸像素都在运数据。

吞吐量有一笔直观的账：1080p 屏幕、方块 8 像素见方时，一屏约 240 × 135 = 3 万多个格子，扣掉面单，一帧能装约 4 KB；每秒播 5 帧，就是每秒约 20 KB。想更快？方块调小、每秒播更多帧就行——接收端的 calibrate 命令会实测当前信道质量，帮你找到能撑住的最快参数。

### 3.2 发送端永远不知道你收到了没有——那怎么保证可靠？

这是理解本系统最关键的一点：**信道严格单向**。光从屏幕射出来，摄像头拍进去，接收端没有任何办法"回话"。发送端不知道你收到了几帧，甚至不知道你有没有在收。

那可靠传输从哪来？靠两个巧妙的配合：

**电视重播 + 随时开机。** 发送端把所有帧**无限循环播放**，像电视里循环重播的节目：你什么时候打开电视（接收端什么时候启动、哪怕中途才加入），迟早都能等到自己缺的那一集。某一帧拍坏了？下一轮它还会来，重新拍就是了。"重传机制"被"无限重播"免费实现了——发送端甚至不需要知道需要重传这回事。

**随播的"包裹清单"。** 文件名、文件大小这些信息不占数据包裹的容量，而是做成一种特殊的**元数据帧**，像电台报时一样，每轮循环的第一帧插播一次、之后每 100 帧再插播一次。接收端哪怕中途才开始听，迟早也能拿到文件名，确定往哪个文件落盘。

### 3.3 几何自举：收到一张"没有说明书的图纸"

想象你收到一张画满黑白格子的纸，没人告诉你格子多大、一共几行几列——怎么读出上面的信息？这就是接收端面对每一帧时的处境。

更别扭的是个死循环：格子的规格（几列几行、方块多大）**就写在帧头里**，可你要先知道格子多大，才能正确地读出帧头。好比拿到一本密码本，钥匙却写在密码本里。

解法是让画面**自带标尺**：四角各有一个白色实心方块——**角标**，协议规定它的边长严格等于格子边长的 3 倍。于是接收端的阅读流程变成：

1. **二值化**：把拍到的画面变成纯黑白（拍照有光线明暗、摩尔纹，所以不是一刀切定阈值，而是逐区域自适应）；
2. **量角标**：找到四角的白色方块，量出边长，**除以 3 就是格子边长**；
3. **数格子**：四角之间能放下多少格，就是几列几行；
4. **交叉验证**：现在可以正确采样、读出帧头了——读出来后跟自己量出的数字再对一遍，对不上说明这帧拍坏了，整帧扔掉。

一次测量同时锁定全部几何参数，而且**全程没有任何默认值**——换屏幕、换方块大小、换分辨率，接收端都自动适应，两端永远不会因为"参数没对齐"而传不下去。

这套机制后来经过两次实战打磨（细节见 [ADR-0001](./adr/0001-角标编码几何自举.md)）：

- **显示缩放问题**：Windows 开 125% / 150% 缩放时，抓屏程序量到的是物理像素，发送页写的却是缩放前的像素，两边量出的数字对不上。解法：发送端先把参数换算成物理像素再声明——从此两边用的是同一把尺子。
- **框选抓屏问题**：接收端可以只框选屏幕上一块区域来抓取，框外留多大边距都行。系统起初假设"画面边缘 = 画布边缘"，核实几何后发现：四角的角标锚定的是**网格本身**，跟画面边缘根本没关系。于是干脆放开约束——框大一点、带点边距，照样解。

### 3.4 可靠性的三道保险

**第一道：坏帧整帧丢弃。** 每帧的 CRC 校验码就是"封条"：读出来的内容和封条对不上，说明这一帧在"运输"（显示 → 拍摄 → 识别）途中出了错，整帧直接扔掉，绝不把可疑数据写进文件。反正下一轮它还会来。误码永远污染不了正在还原的文件。

**第二道：断点续传。** 传几百 MB 要几小时，中途 Ctrl+C、崩溃、误关窗口都难免。接收端把进度记在硬盘上：一张"收到没有"的勾选表（位图）+ 一个按帧号定位写入的数据文件。重启后读回勾选表，**缺哪帧补哪帧**。配合"文件 ID 由文件内容算出"——同一个文件重开发送页 ID 不变——新会话能准确接上旧进度。

**第三道：参数硬锁。** 有一种错误很隐蔽：用旧参数传了一半，中途改了发送端的方块大小接着传。CRC 拦不住它——每一帧自己都是合法的，只是前后两半规格不同，拼起来是废品。所以接收端收到这批任务的第一个帧时就把参数"锁"起来，之后任何一帧参数对不上锁，立即报警拒收，宁可让你清空重来，也不拼出一个坏文件。

### 3.5 顺手的一步：文件名也要防身

接收端往磁盘写的文件名，来自内网侧传来的数据——对它来说这是**不可信输入**。万一里面藏着 `../../evil.txt` 这种路径穿越，或者 Windows 保留名 `CON`、非法字符、超长名字，落盘就可能写到不该写的地方。所以文件名要过七道净化，最后再验一遍"解析出来的路径确实还在 output/ 里面"——落盘永远出不了指定目录。

## 四、工程实现

### 4.1 两端技术选型

**发送端：单文件 HTML，零依赖。** 协议编码、gzip（浏览器原生 `CompressionStream`）、Canvas 渲染、PNG 导出全部内联在一个 `sender.html` 里。内网机器上双击打开就能用，不需要安装任何东西——这对隔离环境是硬约束。渲染细节也讲究：播放时隐藏一切 UI、页面背景与静默区同色、全屏播放不拉伸画布，保证摄像头/抓屏采集到的画面边沿不被污染。播放模式有两种：**全屏播放**（给 camera 拍）和**窗口播放**（画布锁定自然尺寸、四周垫静默边，给 desktop 抓屏）。发送页还能一键复制参数逐 bit 一致的接收端命令，消灭两端手动对参数的错配空间。

**接收端：Python 多模块 CLI。** Python ≥ 3.11，依赖只有 opencv-python、numpy、rich、mss、winotify 五个。模块划分：

```
receiver/
├── __main__.py    # CLI 入口（receive / calibrate 子命令）
├── protocol.py    # 解帧、CRC 校验
├── sources/       # camera / video / images / desktop 统一迭代器接口
├── store.py       # 位图 + 定长文件持久化、断点续传、参数锁
├── restore.py     # 收齐还原（gunzip + 完整性证明）
├── sanitize.py    # 文件名七步净化
├── metadata.py    # 元数据帧解析
├── progress.py    # rich 实时进度（帧数/百分比/KB/s/识别率/丢帧）
└── paths.py       # progress/output/debug 目录锚定脚本目录，不依赖 cwd
```

四种取帧源共用一个迭代器接口，下游识别流水线完全不感知画面来自哪里——camera 通道目前只留了骨架，后续补全不需要动流水线。

### 4.2 测试策略：只有两个缝

这个系统的两端运行在完全不同的环境里（浏览器 vs Python），但它遵守一条很干净的测试原则：**只测外部行为，只有两个测试缝**。

- **缝 A**：发送端浏览器外沿——playwright 驱动 `sender.html` 完成选文件 → 导出 PNG 帧序列；
- **缝 B**：接收端 CLI 外沿——子进程运行 `python -m receiver`，以真实帧序列驱动。

缝 A 的产物直接喂给缝 B，断言还原后的文件与源文件 sha256 一致——这就是端到端闭环测试。协议还有一套独立的 Python 最小编码夹具（`tests/fixture_encoder.py`），它是协议的**第二个独立实现**，专门用来制造异常帧：坏 CRC、参数错配、超长文件名、元数据缺失。两个实现互相交叉校验，防止实现细节绑架协议。CRC 则用独立位级实现与 `zlib.crc32` 双向对照，自检向量 `CRC32(b"123456789") == 0xCBF43926` 锁死参数不漂移。

## 五、可扩展性

协议在设计时就给演进留了门，主要方向：

### 5.1 协议内的扩展空间

- **版本字段**：帧头 `VER` 是预留的升级闸门。任何不兼容变更（比如放开物理 BIT ≤ 15 的 4 bit 上限、改帧结构）都走 VER bump，新旧两端可以按版本协商。
- **几何参数即速率旋钮**：BIT、FPS、COLS/ROWS 都是发送端可调参数，接收端通过几何自举自动适配——**提高吞吐量不需要改协议**，只需要 calibrate 实测找到当前信道质量下的极限参数。摄像头对屏拍摄引入摩尔纹和压缩伪影时，降 BIT、加 PAD 就是现成的降级路径。
- **FLAGS 保留位**：bit15 已用于 gzip，剩余 15 bit 可承载后续特性（如加密标志、分片模式）。
- **压缩方式字段**：元数据帧的压缩方式目前只有 gzip（0x01），换更高效的压缩算法（zstd、brotli）是协议内的平滑升级。

### 5.2 取帧源与信道扩展

- **camera 通道**：统一迭代器接口已留好骨架，补全摄像头对屏拍摄只涉及 `sources/camera.py`，下游流水线（几何自举、CRC、续传）零改动。ADR 里已预判了它的难点——角标测量 ±1 像素误差在小 BIT 下会被放大，calibrate 的 δ 探针通道就是为降质源保留的。
- **更远距离 / 更大屏幕**：投影仪、大屏、多屏拼接都是潜在的"发射器"，几何自举保证了接收端对任意分辨率自适应。
- **反向信道依然是"永不在范围内"**：严格单向是系统的安全立足点（内网侧没有任何数据回流路径），所有扩展都必须在这一前提下成立。

### 5.3 安全增强

当前系统明示**不提供加密与访问控制**（见 spec 的 Out of Scope）。但架构上是平滑可加的：在 gzip 之前/之后插入加密层，只需占用 FLAGS 保留位声明加密方式，帧结构、CRC、续传逻辑全部不动。当然，对一个物理单向信道而言，安全模型本身就和网络传输不同——主要威胁是误码而非窃听。

### 5.4 体验层的自然延伸

多文件打包发送（当前单次一个文件，多任务由接收端多文件进度自然承载）、目录递归传输、接收端 Web 状态页等，都是数据链路之上的应用层工作，不触及协议冻结项。

## 六、小结

这个项目本质上是在回答一个问题：**当唯一的信道是光，怎么把文件可靠地搬出去？**

答案由三层构成：

1. **编码层**——gzip 压缩 + 大帧分片 + 26 字节自描述帧头 + 整帧 CRC，把每一帧变成一块"没有冗余的二维码"；
2. **识别层**——角标编码法解决几何自举悖论，接收端零默认参数，任意屏幕、任意缩放、任意裁切边距都能自适应解析；
3. **信道层**——无限循环重播 + 位图断点续传 + 参数硬锁，在没有反向信道的严苛前提下，依然实现可靠的端到端传输。

它把"屏幕"从一个显示设备变成了一个被动的数据发射器——而这一切的两端，一个是零依赖的 HTML 文件，一个是五个依赖的 Python 包。

# Spec：跨隔离网络单向文件摆渡系统

> 状态：**待发布**（issue tracker 未配置，暂存 `docs/specs/`；配置后发布并打 `ready-for-agent` 标签）
> 事实来源：[需求文档.md](../../需求文档.md) · 术语：[CONTEXT.md](../../CONTEXT.md) · ADR：[0001 角标编码几何自举](../adr/0001-角标编码几何自举.md)

## Problem Statement

内网环境无法联网，也没有任何网络通道或 U 盘等摆渡介质可以把文件送出来。外网侧需要拿到内网的文件，除了"把屏幕当单向光信号发射器"之外没有任何可用信道。目前没有一套可用的工具来完成这件事：手工拍照识别不可靠、二维码方案容量小速度慢、OCR 误码率高，都无法把一个几百 KB 到几百 MB 的文件完整、可校验地摆渡出去。

## Solution

两端各一个程序：

- **发送端**：一个纯浏览器单文件页面（`file://` 直开、零网络请求）。选择文件后 gzip 压缩、分片、封帧，把每帧渲染成黑白方块网格（含角标与静默区）全屏循环播放；同时可导出 PNG 帧序列用于离线闭环自测。
- **接收端**：Python 多模块 CLI（`python -m receiver`）。从四种取帧源（camera / video / images / desktop）拿画面，通过几何自举（角标测量，无默认参数）推导网格、透视校正、采样、CRC 校验，以位图 + 定长文件持久化断点进度，收齐后还原落盘，rich 实时进度，完成时 Windows 通知。

文件经 gzip 尾部 CRC + ISIZE 与 sha256 获得端到端完整性证明。整个系统只有两个测试缝：发送端浏览器外沿与接收端 CLI 外沿。

## User Stories

### 发送端（内网发送操作员）

1. 作为内网发送操作员，我想在浏览器里直接打开一个 HTML 页面选择任意文件，以便不需要安装任何软件就能开始摆渡。
2. 作为内网发送操作员，我想让程序自动完成 gzip 压缩、分片、封帧并全屏循环播放黑白方块帧，以便不需要理解协议细节。
3. 作为内网发送操作员，我想让大文件（最大 256 MB）也能分片成帧播放，以便不受文件大小限制。
4. 作为内网发送操作员，我想让画面整数倍缩放且画布外沿干净（背景同静默区色、隐藏黑色 UI），以便摄像头或抓屏采集到的画面边沿不被污染。
5. 作为内网发送操作员，我想按屏幕自动反推 COLS/ROWS 并在 UI 回显 BIT/FPS/chunkSize 等参数，以便确认当前发送参数。
6. 作为内网发送操作员，我想点击"一键复制接收端命令"拿到参数一致的接收端命令，以便两端参数逐 bit 对齐、不出错配。
7. 作为内网发送操作员，我想导出 PNG 帧序列 + frames.json，以便离线完成闭环自测、不依赖摄像头。
8. 作为内网发送操作员，我想让同一文件每次打开页面都派生同一个 fileId，以便接收端断点续传能命中已有进度。
9. 作为内网发送操作员，我想让程序无限循环重播全部帧，以便在严格单向信道下接收端随时加入都能收齐。
10. 作为内网发送操作员，我想让元数据帧（文件名/大小/压缩方式）每轮首帧和每 100 帧插入一次，以便接收端中途加入也能拿到元数据。

### 接收端（外网接收操作员）

11. 作为外网接收操作员，我想用一条命令指定取帧源（images/desktop/video/camera）开始接收，以便不同场景用同一套工具。
12. 作为外网接收操作员，我想让接收端不依赖任何硬编码默认参数、自动从画面角标推导几何参数，以便发送端换参数后我无需手工对齐。
13. 作为外网接收操作员，我想让坏帧被 CRC 整帧丢弃，以便误码不会污染正在还原的文件。
14. 作为外网接收操作员，我想让进度按文件实时显示帧数/百分比/KB/s/识别率/丢帧，以便判断当前信道质量。
15. 作为外网接收操作员，我想在 Ctrl+C 或崩溃后重启继续只补缺失帧，以便长时间传输不被中断报废。
16. 作为外网接收操作员，我想在同一 fileId 的发送端参数变更时收到明确告警并被拒绝续传，以便我不会拿旧进度拼出新参数下的坏文件（硬锁，需手动清理任务目录后重收）。
17. 作为外网接收操作员，我想在收齐数据帧且收到元数据帧后自动 gunzip 还原到 output/ 并获得 gzip 尾部完整性证明，以便拿到与源文件 sha256 一致的文件。
18. 作为外网接收操作员，我想在元数据帧缺失时数据帧照常落盘但不启动还原，以便坏元数据不会导致错误还原。
19. 作为外网接收操作员，我想让恶意文件名（路径穿越/保留名/非法字符/超长）被七步净化并经 resolve() 二次校验，以便落盘永远不出 output/。
20. 作为外网接收操作员，我想在还原完成时收到 Windows 桌面通知 + 声音，以便不用盯着终端等待。
21. 作为外网接收操作员，我想在缺少通知依赖时自动降级为终端高亮提示，以便低配环境仍能收到完成信号。
22. 作为外网接收操作员，我想用 calibrate 子命令统计识别率/CRC 通过率并获得推荐参数回灌，以便用数据确认最终发送参数。
23. 作为外网接收操作员，我想让 desktop 通道具备变化检测、稳定两帧判定、超时强制解码和 --region 区域捕获，以便适配 RDP 渐进刷新与局部窗口。
24. 作为外网接收操作员，我想用 video 源解析预先录制的发送端屏幕视频，以便离线复盘与批量验证。
25. 作为外网接收操作员，我想让 progress/output/debug 目录锚定脚本目录而不依赖 cwd，以便从任意工作目录启动都不散落文件。
26. 作为外网接收操作员，我想让还原成功后自动清理 payload，以便磁盘不被已还原任务的残留数据撑爆。

### 开发与维护者

27. 作为开发者，我想让协议（帧头/CRC/元数据/角标规则/参数锁定）有单一冻结文档和跨端自检向量（`CRC32(b"123456789") == 0xCBF43926`），以便两端实现有唯一对齐基准。
28. 作为开发者，我想让整个系统只有两个测试缝（发送端浏览器外沿、接收端 CLI 外沿）加一个 tests/ 内的独立 Python 编码夹具，以便测试覆盖端到端行为而不绑定实现细节。
29. 作为开发者，我想让端到端闭环测试（导出 PNG → images 解码 → sha256 一致）进 pytest，以便每次改动都能自动验证协议一致性。
30. 作为开发者，我想让文件名净化、CRC、参数锁定拒绝路径都有表驱动单测，以便边界行为被精确锁定。
31. 作为维护者，我想让 camera 通道只留统一迭代器接口骨架、desktop 与 video 共用稳定帧/伪影容错逻辑，以便后续扩展不重写流水线。

## Implementation Decisions

- **协议冻结**（详见需求文档 §3）：26 字节帧头（SYNC/VER/FILE_ID/FRAME_NO/TOTAL_FRAMES/DATA_LEN/CHUNK_SIZE/COLS/ROWS/GEO/FLAGS/CRC32）、CRC-32/ISO-HDLC、元数据帧 12+nameLen 布局、角标 = 3×BIT。帧头仅同步字不参与 CRC。
- **几何自举**（ADR-0001）：接收端无默认参数，测角标白块边长 ÷ 3 得 BIT，画布尺寸得 COLS/ROWS，与帧头交叉校验，不一致整帧丢弃。
- **参数锁定**：同一 fileId 首帧落地时锁定 fileId + 几何 + chunkSize 进 meta.json；此后参数不一致整帧拒绝 + 告警，旧进度作废需手动清理（硬锁）。
- **模块划分**：发送端为浏览器单文件（协议编码 + Canvas 渲染 + 导出，全部内联）；接收端为多模块包（sources 统一迭代器接口、pipeline 识别流水线、store 持久化与续传、cli 子命令入口），入口 `python -m receiver`。
- **CLI 契约**：`receive --source images|desktop|video|camera [--dir|--video|--region|--out]` 与 `calibrate [--source ...]`。
- **持久化**：received.bin 位图 + data.bin 定长写入；meta.json 原子写（tmp + os.replace）；未完成任务惰性加载；还原成功清理 payload。
- **还原判据**：数据帧齐 ∧ 元数据帧已收；gunzip 尾部 CRC+ISIZE 作端到端证明。
- **依赖**：接收端 Python ≥ 3.11 + requirements.txt + venv（opencv-python、numpy、rich、mss、winotify）；发送端零依赖；不引入 Electron、不引入打包工具。
- **里程碑**：M1 协议 + 发送端 + images 闭环；M2 desktop + video + 续传 + 进度；M3 calibrate + 通知 + 错配防御 + camera 骨架。

## Testing Decisions

- **只测外部行为**：不 mock 流水线内部；断言对象是 CLI 退出码/终端输出、`output/` 与 `progress/` 的落盘结果、导出目录内容。
- **两个缝**：
  - 缝 A（发送端浏览器外沿）：playwright 驱动 sender.html 完成选择文件 → 导出，产出 frames_png + frames.json。
  - 缝 B（接收端 CLI 外沿）：子进程运行 `python -m receiver`，以真实/夹具帧序列驱动。
- **端到端**：缝 A 产物直喂缝 B（`--source images --dir`），逐帧字节一致 + gunzip 后 sha256 一致——即验收标准 1 的自动化。
- **夹具制造器**：tests/ 内独立 Python 最小编码器，构造参数错配、超长文件名、坏 CRC、元数据缺失等异常帧；它是协议的独立实现，兼作交叉校验，不进入 receiver 包。
- **纯函数直测**：CRC 自检向量、文件名七步净化表驱动用例（`../../evil.txt`、`..\..\x`、`CON`、200 字节边界）、封解帧往返、参数锁定拒绝路径。
- **desktop/video 通道**：与 images 共用缝 B，夹具为预录视频/图像序列（含噪点注入用例验证误码不污染）。

## Out of Scope

- camera 通道的完整实现（仅统一迭代器接口骨架；后期主流通道为 desktop 与 video）
- 加密与访问控制（N6 明示当前不提供）
- 反向通道 / 发送端接收确认（严格单向，永不在范围内）
- Electron / 打包分发、Python < 3.11 兼容
- 多文件打包发送、目录递归传输（单次一个文件，多任务由接收端多文件进度自然承载）

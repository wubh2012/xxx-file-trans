# 喷泉码实验版本

从 `v1.1.0` 起随主分支与 Windows Release 提供；最初开发于
`codex/fountain-experiment` 分支。默认仍使用原有固定 FEC。
实验模式是每组 32 分片的系统式 GF(2) 随机线性喷泉码，不是 LT/RaptorQ。
用于验证丢帧后持续发送新修复帧，能否缩短完整文件重播带来的等待。

## 为什么引入喷泉码

这个项目只有“发送端显示画面 → 接收端读取画面”的单向通道。
接收端发现少了某一帧，无法回头告诉发送端“请再发这一帧”。原来每 32 个
数据帧附加 2 个固定校验帧，可以补齐同组最多 2 个缺帧；超过这个范围，
就要等下一轮重播。文件已经收到 99%，也可能因为最后几帧一直等很久。

引入喷泉码，就是让发送端不断给出新的修复信息。接收端可以用这些信息
算出缺失内容，减少等待某个原始帧再次出现的时间。决策与取舍记录在
[ADR-0004](adr/0004-系统式喷泉码与持续修复.md)。

## 用通俗的话理解喷泉码

可以把文件想成一副拼图。普通重播是反复发同一套拼图碎片；喷泉码除了
发碎片，还不断发“几块碎片之间的关系”。这些关系本身不会减少文件信息量，
却能在部分碎片丢失后，帮助接收端推算缺的内容。

例如文件拆成 A、B、C 三块，发送端另外发一个修复帧：

```text
R = A XOR B
```

XOR 叫“异或”，可以理解为一种能抵消重复数据的运算：同一份数据参与两次
就会抵消。如果 B 丢了，但收到 A 和 R，就可以计算：

```text
B = R XOR A
```

再收到 `S = B XOR C`，还可以用刚恢复的 B 算出 C。实际实现会选择不同的
分片组合，接收端累计并求解这些关系。不是每个修复帧都能立即补一块：
如果缺失太多，或者新关系与已有关系重复，还需要继续接收。

它叫“喷泉码”，是因为发送端可以像喷泉一样不断产生修复帧。
接收端更关心“新收到的信息是否足够恢复文件”，无需一直追某个指定的原始帧。

## 在本项目里如何结合两种方式

我们采用“系统式”方案，也就是保留直接发送原始数据的路径：

```text
首轮：原始帧为主，每 32 个原始帧穿插 2 个修复帧（默认比例）
之后：持续发送新的修复帧，并定期发送文件元数据
接收：直接保存原始分片，利用修复帧求解缺失分片，收齐后还原文件
```

这样原始帧收到就能直接使用，出现丢帧时再利用修复信息；修复方程也可以
提前保存，等待后面的原始帧到达后继续求解。原始帧仍按组间交错播放，
让一段连续丢帧尽量分散到不同组。接收端已经恢复的分片照常落盘，支持续传。

当前使用每组最多 32 个分片的 XOR 随机线性组合，不是标准 LT/RaptorQ。
修复只在组内进行，不保证收到和原始分片数一样多的帧就一定恢复成功。

## 能带来哪些提升，代价是什么

- **少等整轮重播**：同组缺失超过两个原始帧时，仍可继续收到新修复信息，
  不必完全依赖原始帧再次出现。
- **适合单向通道**：接收端不需要反馈缺帧清单，发送端可以持续修复。
- **改善接近完成时的等待**：原始帧与修复帧共同补齐文件，尤其针对
  “大部分已经收到，最后少数分片迟迟收不齐”的情况。
- **保留原有使用方式**：固定 FEC 仍是页面默认模式，喷泉码可单独选择；
  接收端自动识别，无需手动选择解码算法。

本机同一份 **1 MiB 文件、30 FPS、每种配置三次**的真实桌面对照：

| 条件 | 原固定 FEC | 喷泉码 32:2 | 实际变化 |
|---|---:|---:|---|
| MSS 抓屏 | 33.216 秒 | 21.239 秒 | 中位耗时缩短 36.1%，约 1.56 倍吞吐 |
| DXGI 稳定抓屏 | 15.980 秒 | 16.921 秒 | 中位耗时增加 5.9% |

MSS 下，从收到至少 95% 到完成的中位等待由 12.508 秒降至 2.317 秒。
这说明主要收益来自补齐丢帧，而不是让单张画面识别更快。
15 次有效实测全部通过 SHA-256 校验，详细条件与原始数据见
[穿插修复对照报告](../benchmark/results/report-fountain-interspersed-20261003.md)。

修复帧占用发送时隙，编码和解码也需要计算。因此几乎不丢帧的链路可能
更慢；穿插修复也不保证比原来的首轮尾部修复更快。32:1、32:2、16:1、8:1
四种比例都保留，便于在目标链路测试选择。本次 MSS 实测 32:2 最快，
所以保留它作为喷泉码默认比例，固定 FEC 仍是整个页面的默认模式。

以上是本机少量重复的结果，不能当成所有电脑、文件大小或摄像头场景的
提速承诺。旧版接收端不支持 v2，启用喷泉码要配套使用新版接收端。

## 使用

1. 使用 `v1.1.0` 或当前源码的 `sender.html`，在“纠错模式”选择“喷泉码（实验 v2）”。
2. 配套使用 `v1.1.0` 或当前源码的接收端；GUI 和 CLI 自动识别，无需额外参数。
3. 首轮以原始分片为主，默认每 32 个原始帧穿插 2 个修复帧；可选择
   32:1、32:2、16:1、8:1。修复编号轮流覆盖各组，原始帧仍按组间交错发送。
   第一轮结束后只发送新修复帧。
4. 等接收端确认还原后停止。修复批次不代表完整文件重播轮次。

同一文件切换纠错模式时，应清空其旧的未完成任务进度。已恢复分片可断点续传，
尚未解出的修复方程只存内存，重启后重新累计。原有视频制作工具仍输出 v1。

导出 PNG 在首轮穿插修复帧之后，再附每组 16 个修复帧（默认首轮每组 2 个），
是有限序列，不保证任意损失或中途开始都能恢复；
在线播放则持续生成新修复帧。修复编号耗尽后重新发送原始数据轮次。

## 对比方法

固定种子仿真：

```powershell
.venv/Scripts/python.exe benchmark/run_bench_fountain.py --seeds 20
```

仿真同时比较固定 FEC、改造前的首轮尾部修复，以及四种穿插比例；记录
90%、95%、99% 到收齐的等待时间。浏览器测试校验仿真与实际发送序列一致。
真实桌面测试通过 `--repair-ratio 32:2` 选择比例。

真实桌面测试（两次必须使用同一文件、FPS、窗口和采集后端；依次运行）：

```powershell
.venv/Scripts/python.exe benchmark/run_bench_live.py --input sample.bin --capture dxgi --coding fec --fps-list 30 --reps 2 --skip-calibration --trace --run-label fec-test
.venv/Scripts/python.exe benchmark/run_bench_live.py --input sample.bin --capture dxgi --coding fountain --fps-list 30 --reps 2 --skip-calibration --trace --run-label fountain-test
```

此实验不使用 calibrate 的重复轮次指标评价喷泉码；新修复帧并不重复原始帧。
结果应同时看 SHA-256、端到端 wall 时间、99% 后等待、拒帧和队列丢弃。
仿真的帧数/FPS 只代表信道占用，未包含抓屏、网格识别、磁盘和浏览器调度。

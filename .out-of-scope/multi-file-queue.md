# 多文件队列

本项目不做发送端多文件队列（批量摆渡逐个播放）。

## Why this is out of scope

单文件「选文件 → 播放 → 接收端还原」已覆盖当前摆渡场景，批量化属于体验优化而非能力缺口。更根本的是，多文件连续播放与协议的参数锁定设计直接冲突：

协议 §6 参数锁定是硬锁——接收端 FrameStore 在首个数据帧落地时锁定 fileId + 几何参数（COLS/ROWS/BIT/PAD/chunkSize），此后跨任务 fileId 的帧头被整帧拒绝（`FrameRejected('file_id')`），不自动作废、不重开任务。这是防止异任务帧毒化已收进度的设计。要在同一接收会话内连续发多个文件，必须先设计「任务切换检测」机制（如静默间隔判据 + 安全重开任务），该机制触及协议冻结项边界与防毒化论证，成本显著高于当前需求价值。

若未来重新考虑，入口是先设计并验证接收端任务切换机制（防毒化论证 + e2e），再动发送端队列。
